# 排错手册（分层版）

## 0. 总原则

```
先定位在哪一层，再在那一层里查。不要一上来就 Google 报错原文。
```

**分层切分法**：任何一次报错，先问三个问题——
1. **它是在哪个进程里报的？**（launch 里有五六个节点，报错前缀 `[move_group-2]` 已经告诉你了）
2. **上游有没有正常？**（规划成功 → 问题在执行侧，直接砍掉一半）
3. **报错的层 = 根因的层吗？**（多半不是）

**四层速查**：

| 层 | 先敲什么 |
| --- | --- |
| 硬件 | 指示灯颜色、`lsusb`、`sudo dmesg --follow`、`ip link` |
| 通信 | `ros2 node list`、`ros2 topic info X --verbose`、`sudo ss -ltnp \| grep 50051` |
| 环境 | `head -1 <可执行文件>`、`which python3`、`echo $PYTHONPATH`、`pip show <pkg>` |
| 算法 | 维度、键名、归一化范围、`error_code` |

## 1. ROS 2 / MoveIt 2

### `Package 'airbot_play_movit_config' not found, searching: ['/opt/ros/jazzy']`
只加载了系统 ROS 2，没加载工作空间。搜索路径里只有 `/opt/ros/jazzy` 就是铁证。
```bash
cd <工作空间根目录>
source /opt/ros/jazzy/setup.zsh
source install/setup.zsh
ros2 pkg prefix airbot_play_movit_config   # 应返回工作空间里的路径
```

### zsh 里 `source setup.bash` 报 `没有那个文件或目录: .../setup.sh`
`setup.bash` 用 `$BASH_SOURCE` 定位自己，zsh 里这个变量是空的，于是拿 **cwd** 去拼 `setup.sh`。
```bash
source /opt/ros/jazzy/setup.zsh    # zsh 用 zsh 后缀
source install/setup.zsh
```
写脚本时自动判断：
```bash
if [ -n "$ZSH_VERSION" ]; then _sfx=zsh; else _sfx=bash; fi
source /opt/ros/jazzy/setup.$_sfx
```

### 编译报 `No module named 'catkin_pkg'`
CMake 找到的是 Conda 的 Python，但那个环境里没装 ROS 的构建依赖。
```bash
python3 -m pip install catkin_pkg "empy==3.3.4" lark
colcon build --symlink-install --cmake-clean-cache
```
> `empy` 必须锁 3.3.4，新版 API 变了。

### Fast CDR `undefined symbol: eprosima::fastcdr::Cdr::serialize`
MoveIt2 / ros2_control / Fast DDS 的 apt 包版本不一致（典型是只升了一半）。
```bash
sudo apt install --only-upgrade \
  ros-jazzy-fastcdr ros-jazzy-fastrtps \
  ros-jazzy-rosidl-typesupport-fastrtps-c ros-jazzy-rosidl-typesupport-fastrtps-cpp \
  ros-jazzy-rmw-fastrtps-cpp ros-jazzy-rmw-fastrtps-shared-cpp
```
升完**关掉所有旧终端**再重启 demo（旧进程还链着旧 so）。

### `ros2 control` 不是有效子命令
```bash
sudo apt install ros-jazzy-ros2controlcli
```
另外 `ros2 control list_controllers` 需要 `/controller_manager` 在跑，demo 没起时它会一直等——**不是卡死**。

### `Loader for controller 'joint_state_broadcaster' not found`
```bash
sudo apt install ros-jazzy-joint-state-broadcaster
```
装完要**整个重启 demo**，controller_manager 只在启动时扫描插件。

### `ros2 topic echo --once /joint_states` 一直不返回
它在等第一条消息。一直等 = 现在没有数据。
```bash
timeout 3 ros2 topic echo --once /joint_states     # 加超时，别干等
ros2 topic info /joint_states --verbose            # 看 Publisher count
```
- `Publisher count: 0` + 仿真 → `joint_state_broadcaster` 没装 / 没 active
- `Publisher count: 0` + 真机 → `/airbot_play` 节点没起来（见下）
- `Publisher count: 2` → 仿真和真机同时开着，先停一个

### `Plan` 和 `Plan & Execute` 看起来一样
RViz 两种操作都会播放预览动画。**只信 `/joint_states.position`**：
```bash
ros2 topic echo --once /joint_states > /tmp/a.yaml
# 操作
ros2 topic echo --once /joint_states > /tmp/b.yaml
diff -u /tmp/a.yaml /tmp/b.yaml     # header.stamp 变是正常的，position 变才是执行了
```

### ⭐ 真机能规划，`Plan & Execute` 返回 `CONTROL_FAILED`
```
Motion plan was computed successfully.
Didn't receive robot state (joint angles) with recent timestamp within 1.000000 seconds.
Failed to validate trajectory: couldn't receive full current joint state within 1s
```
**按顺序查**：
```bash
ros2 node list | grep airbot                  # 1. 有没有 /airbot_play
ros2 topic info /joint_states --verbose        # 2. Publisher count 是不是 0
head -1 install/airbot_play/lib/airbot_play/airbot_play_node    # 3. 用哪个解释器
/usr/bin/python3 -c "import airbot_hardware_py"                 # 4. 那个解释器能不能 import
```
根因通常是 3+4：shebang 是 `#!/usr/bin/python3`，SDK 只装在 Conda 里。
```bash
conda activate airbot_moveit2
export PYTHONPATH="$CONDA_PREFIX/lib/python3.12/site-packages:$PYTHONPATH"
/usr/bin/python3 -c "import rclpy, airbot_hardware_py; print('OK')"
```
**这个 export 只对当前终端有效**，每开一个真机终端都要重来。

### 规划失败，error_code 怎么读
```
 1 SUCCESS   -1 FAILURE   -2 PLANNING_FAILED   -4 CONTROL_FAILED
-10 START_STATE_IN_COLLISION   -12 GOAL_IN_COLLISION
-18 NO_IK_SOLUTION   -31 INVALID_GOAL_CONSTRAINTS   99999 UNDEFINED
```
配合 move_group 日志看：
- `Joint X is constrained to be below the minimum bounds` → 目标越限位
- `Unable to sample any valid states for goal tree` → 目标区域采不到合法点（越限位/被碰撞占满/容差太紧）
- `Unable to find solution by any of the threads in N seconds` → 看 N：**远小于 `allowed_planning_time` = 目标非法；接近 = 采样确实难**
- `START_STATE_IN_COLLISION` → 当前姿态就是碰撞的，先手动挪开再规划

## 2. 硬件 / CAN（真机专用，仿真用不到）

### 找不到 `can0`
```bash
ip link | grep -E 'can[0-9]+'
sudo modprobe slcan          # 加载 SocketCAN 串行驱动
lsusb                        # 确认 USB 设备被识别
sudo dmesg --follow          # 保持运行，重新插拔 USB-2 观察
```
常见原因：接错了口（控制口是 **USB-2 Type-C**，USB-1 是相机数据口）、用了只供电不传数据的线。

### `No buffer space available`
CAN 发送队列满了，通常是警告不是错误。
```bash
sudo ip link set can0 txqueuelen 1000
```

### `Motor N init failed, expected 7 params, got 6`
**型号参数 `-t` 写错了**，固件协议对不上。这是当时最坑的一个——试了 `airbot_replay_mini` 不行，
改成 **`airbot_play_e2`** 才通。
```
机械臂端：airbot_play / airbot_play_g2 / airbot_play_g2l / airbot_play_g2_d405
示教器端：airbot_play_e2 / airbot_replay / airbot_replay_mini
```

### 灯带含义
| 灯 | 含义 |
| --- | --- |
| 黄灯常亮 | 自检中 |
| 黄灯闪烁 | **零位丢失** → 长按底座按钮 3 秒，对齐刻度，再按一次 |
| 红灯常亮 | 自检失败 → 停手，记录日志，联系售后 |
| 白灯常亮 | 自检完成，没检测到 USB |
| 白色呼吸 | USB 已连接，等控制服务 |
| 绿色流动 | 控制服务初始化中 |
| 绿色常亮 | **就绪，可接受指令** |

### 端口被占用 / 拿不到控制权
```bash
sudo ss -ltnp | grep 50051      # 找到旧服务
```
V5.2 用**独占 Lease（租约）**，同一时刻只能有一个客户端持有控制权。关掉其他客户端等租约释放。
多设备必须用不同 CAN 口 + 不同端口：
```bash
sudo airbot-arm -i can1 -t airbot_play_g2l --address 0.0.0.0:50052
```

### 紧急停止顺序
```
SDK 程序终端 Ctrl+C
  → arm-sdk examples run airbot_example_arm_emergency_stop
  → 服务终端 Ctrl+C
  → 从底座 Base Board 拔 24V 电源
```
`Ctrl+C` 卡死时：`pkill -f arm-sdk`。**异常时优先按物理急停，不要等 Ctrl+C。**

**Git LFS 的文件没拉下来**，`.stl` 现在还是几百字节的文本指针。

加速：
```bash
git config lfs.concurrenttransfers 32
git lfs pull --exclude="assets/videos"     # 排除用不上的演示视频
```

### 无显示器跑 MuJoCo
```bash
export MUJOCO_GL=egl      # 有 NVIDIA 卡，离屏渲染（推荐）
export MUJOCO_GL=osmesa   # 纯 CPU 软渲染，慢但最兼容
```

### Hydra 报 `Could not override 'X'. To append to your config use +X=...`
Hydra 的 struct 模式：**配置里已有的 key 用 `k=v` 覆盖，配置里没有的 key 必须用 `+k=v` 新增**。
```bash

aao_demo --config-name pick_and_place task.seed=7                # seed 已存在
```

## 4. LeRobot / 训练推理

### `HFValidationError`：本地路径被当成 repo id
`policy.path` 用了相对路径。
```yaml
policy:
  path: /绝对/路径/到/checkpoints/last/pretrained_model
  local_files_only: true
```

### pip / uv 装 torch 卡住不动（不报错，就是慢）
**先测速，别干等。** 本次实测同一时刻：

```bash
for m in https://mirrors.aliyun.com/pypi/simple \
         https://mirrors.ustc.edu.cn/pypi/simple \
         https://pypi.tuna.tsinghua.edu.cn/simple; do
  host=$(echo "$m" | sed 's|https://\([^/]*\).*|\1|')
  timeout 15 curl -so /dev/null -w "$host => %{speed_download} B/s\n" --noproxy '*' "$m/numpy/"
done
```

```
mirrors.aliyun.com          => 5238512 B/s      ← 换这个
mirrors.ustc.edu.cn         => 3396372 B/s
pypi.tuna.tsinghua.edu.cn   =>  286222 B/s      ← 被限速，torch 装了 20 分钟没装完
```

切换：
```bash
export UV_DEFAULT_INDEX=https://mirrors.aliyun.com/pypi/simple   # uv
export PIP_INDEX_URL=https://mirrors.aliyun.com/pypi/simple      # pip
```
**教训：镜像源的速度是会变的（限速、维护、时段），"清华最快"是刻板印象不是事实。
装大包之前花 15 秒测一次速，能省 20 分钟。** 同理适用于 `HF_ENDPOINT`。

### 镜像下载慢的终极解法：aria2c 多线程 + 正确的 User-Agent

单连接被限速时，多线程能拉起 10 倍以上。本次实测：uv 单线程 300 KB/s → aria2c 16 线程 **15 MB/s**。

**先解析出 wheel 直链，再多线程下，最后离线装：**

```bash
# 1) 让 uv 解析出完整依赖清单（含精确版本）
uv pip install --dry-run "torch==2.7.1" "torchvision==0.22.1" "lerobot[smolvla]" \
  | grep -E "^\s*\+" | sed 's/^\s*+ //' > pkglist.txt

# 2) 从镜像的 simple 索引解析每个包的 wheel 直链（注意过滤架构！）
#    见 sim-rerun/scripts/ 里的 geturls.py

# 3) aria2c 多线程下载  ★ --user-agent 是关键
aria2c -i wheel_urls.txt -j 5 -x 16 -s 16 -k 2M --continue=true \
       --user-agent="pip/24.0" --auto-file-renaming=false

# 4) 离线安装
uv pip install --no-index --find-links /tmp/wheels -r pkglist.txt
```

**两个必踩的坑：**

1. **不带 `--user-agent` 会被镜像 403**
   aria2c 的默认 UA 被阿里云 PyPI 镜像拒绝，而且是**每个文件立刻 403**，
   看起来像"链接都失效了"。`curl` 手测同一个 URL 却是 200 —— 因为 curl 的 UA 不在黑名单。
   **诊断要点：curl 能下、aria2 全部 403 → 十有八九是 UA。**

2. **解析索引时必须过滤 CPU 架构和 Python 版本**
   简单地"取最后一个 .whl"会拿到 `riscv64` / `aarch64` / `i686` / `macosx` 的包。
   过滤条件：文件名含 `x86_64` 或以 `-any.whl` 结尾；Python tag 是 `cp312` / `py3-none` / `cp3X-abi3(X≤12)`。

**另一个更根本的教训：不要用最新的 CUDA 版本。**
本次 torch 默认拉的是 **cu13** 系列 wheel（`nvidia-*-cu13`），国内镜像基本没缓存，
只能回源，速度 300 KB/s；换成 **cu126**（`torch==2.7.1`，依赖 `nvidia-*-cu12`）后，
同一个镜像 2.5 MB/s。**镜像的价值在于"已经缓存"，新版本等于没有镜像。**
显卡是 Ada（sm_89），cu124/cu126 完全够用，追最新 CUDA 没有任何收益。

### ⭐ 大文件下载完了，但模型加载出来是错的 —— 一定要校验 sha256

本次真实翻车：SmolVLM2 骨干 2.03 GB 下"完"了，文件大小分毫不差，
`safetensors` 也能正常打开、能读出张量，**但 sha256 对不上**。

```bash
# HuggingFace 侧的期望值（LFS 文件的 oid 就是 sha256）
curl -s "https://hf-mirror.com/api/models/<org>/<repo>/tree/main?expand=1" \
  | python3 -c "import sys,json
for e in json.load(sys.stdin):
    if e['path']=='model.safetensors': print(e['lfs']['oid'], e['size'])"
# 本地
sha256sum model.safetensors
```

```
期望 b9bfd456c9472c0acd5719d6e514c4b859891af205ee1a736552fd3497b8b0c3
实际 e3e3b2961bef24c5a8b410ee02cb912c14c27c7732f02fc9efd241eda4de90cc   ← 不一致
```

**根因**：我用 `aria2c --continue` **跨不同镜像续传同一个文件**
（先 hf-mirror，中途换 huggingface.co 走代理，又换回来）。
HF 的 LFS 下载会 302 重定向到 CDN，**不同镜像/不同时刻的重定向目标未必是同一份字节流的同一偏移**，
多连接分片写入就在文件里留下了空洞。文件大小是对的（aria2 按最大偏移预分配），内容是错的。

**为什么危险**：
- `safetensors` 只读 header，**不校验数据区**，所以能"正常打开"
- 空洞区域是零字节，加载成模型就是**部分权重被清零**
- 训练/推理不会报错，只会**效果莫名其妙地差**——这是最难查的一类 bug

**规则（三条）：**
1. **同一个文件只用一个源续传。** 换源就删掉重下，不要 `--continue`。
2. **每个大权重下完必须校验 sha256**，别只看文件大小。
3. 多连接下载（`aria2c -x16`）用于**一次性下完**的场景很好；
   用于**反复中断续传**的场景要格外小心，尤其是走 CDN 重定向的链接。

对照组：同一批里用**单一源一次下完**的 `lerobot/smolvla_base`（906 MB），sha256 一次就对。

**修复**：删掉重下，单流不分片：
```bash
rm -f model.safetensors model.safetensors.aria2
curl -L --noproxy '*' -A "pip/24.0" --retry 8 --retry-delay 3 --retry-all-errors \
  -o model.safetensors "https://hf-mirror.com/<org>/<repo>/resolve/main/model.safetensors"
sha256sum model.safetensors    # 必须和期望值一致才能用
```

### 显存 OOM
按代价从小到大加：
```
1. PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True   # 几乎无代价，减少碎片
2. use_amp: true                                       # 几乎无代价
3. gradient_checkpointing: true                        # ~30% 算力代价
4. batch_size 减小 + grad_accumulation_steps 补回      # 影响收敛
5. freeze_vision_encoder: true                         # 影响效果
```

### `KeyError: 'observation.language.tokens'`（lerobot 0.6+ 推理）

直接把原始观测喂给 `policy.select_action(batch)` 会报这个。
**lerobot 0.6 把预处理拆成了独立的 processor pipeline**，策略只吃处理后的 batch。

```python
from lerobot.policies.factory import make_pre_post_processors
pre, post = make_pre_post_processors(policy.config, pretrained_path=ckpt)

batch  = pre(batch)                          # ① 语言 tokenize ② 按训练集统计量归一化 ③ to(device)
action = post(policy.select_action(batch))   # 反归一化回真实动作量纲
```

**两个都不能漏**：
- 漏 `pre()` → 直接报 KeyError，容易发现
- **漏 `post()` → 不报错**，但动作停留在归一化空间，机械臂会乱动。**这是最危险的一种**

> 这就是"特征契约"在推理侧的完整形态：不只是键名和维度对上，
> **归一化和 tokenize 也必须走训练时同一套流水线**。

### 训练 loss 曲线画出来是阶梯状
不是训练的问题，是**日志解析的问题**。lerobot 把 step 打成缩写：
```
step:5K ... step:5K ... step:6K       ← 5100 和 5900 都写作 5K
```
直接 parse 这个字段会让十个点落在同一个 x 上。
**用记录序号 × `log_freq` 重建真实步数**：
```python
steps.append(len(loss) * LOG_FREQ)   # LOG_FREQ 与 --log_freq 一致
```
> 这种 bug 不看图形状根本发现不了——**画完图一定要问一句"这个形状合理吗"**。

### 评测成功率怎么报才不算骗人
三条硬规则：
1. **必须有对照组**。脚本化专家/人类遥操作在同一批 seed 上的成功率是上界，
   只报策略的数字没有意义。
2. **必须有置信区间，且用 Wilson**。
   正态近似 `p ± z·√(p(1-p)/n)` 在 p=1 时宽度为 0，等于宣称"100% 绝对可靠"。
   ```python
   def wilson(k, n, z=1.96):
       p = k/n; d = 1 + z*z/n
       c = (p + z*z/(2*n))/d
       h = z*math.sqrt(p*(1-p)/n + z*z/(4*n*n))/d
       return max(0,c-h), min(1,c+h)
   ```
   40 次全对 → [91.2%, 100%]，这才是诚实的说法。
3. **区分"超时"和"stage 失败"**。
   `failed_stage_counts` 为空 + `steps == max_updates` = 策略卡死超时，
   和"抓空了""放偏了"是完全不同的失效模式，根因和对策也不同。

### 归一化 / 维度报错
**特征契约没对齐**。训练和推理两侧必须完全一致：
- `observation.state` 维度（`[arm]`→6，`[arm, eef]`→7，EEF 位姿+夹爪→8）
- 相机**键名**和分辨率（插件里写裸名 `camera1`，LeRobot 自动加 `observation.images.` 前缀）
- `action` 维度
改了状态维度还要同步改 `config.json` 的 `max_state_dim` / `max_action_dim`。

## 5. 这次复现里新踩的坑

| 现象 | 根因 | 解法 |
| --- | --- | --- |
| `colcon build` 4 个包只花 2.5 s | `airbot_play_msgs` 的 `rosidl_generate_interfaces` 整段被注释，是空壳包 | 不是问题，但要知道 |
| RViz 报 `/recognize_objects not available` | 没接物体识别，RViz 面板的可选功能 | 忽略 |
| RViz 报 `No 3D sensor plugin(s) defined for octomap` | 没配深度相机，八叉树避障未启用 | 忽略；要避障才需要配 |
| `git lfs pull` 直连 GitHub 卡在 35 MB | LFS 对象在 S3 CDN 上，直连不通 | 走代理 + `lfs.concurrenttransfers 32` |
| LFS 走代理只有 93 KB/s，直连 200 KB/s | 代理带宽比直连低 | 大文件先测速再选路：`curl -w "%{speed_download}"` |
